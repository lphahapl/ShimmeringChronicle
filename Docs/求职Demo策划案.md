# 《边境哨站：失控守卫》求职 Demo 策划案

版本：v1.0 ｜ 工程盘点：2026-09-27 ｜ 目标平台：Windows PC

## 1. 项目目标

把当前 Unity 工程制作成一段 **15～20 分钟、能独立启动、能失败重试、能通关**的动作冒险体验。展示重点是 Unity 客户端开发能力：数据配置与运行状态分离、事件驱动的系统协作、动画与战斗同步、可调参数、问题定位与完整交付。

默认面向 Unity 游戏客户端／玩法程序岗位。玩法、地图和数值均为本案提议；工程现状来自源代码与已保存资源检查，不代表所有功能都已完成运行验收。

作品的核心演示句：**玩家通过对话接受委托，在探索和战斗中获得第二种武器，完成任务解锁 Boss，利用两种武器的不同节奏击败 Boss 并领取奖励。**

优先证明一个完整体验，而不是分别打开背包、对话、Boss 三个互不相干的测试场景。

## 2. 目前有哪些系统，完成到什么程度

这里的“闭环”要求有输入、状态变化、反馈和结束／重置路径。只有接口、配置字段或动画播放，不能算完整玩法系统。

| 系统 | 工程中已有的依据 | 判断与剩余工作 |
| --- | --- | --- |
| 物品配置与运行数据 | ItemSO、BasicItemSO、WeaponSO；ItemData、WeaponData；CreateData 与 Clone；GameManager 按 ID 加载配置 | 数据组织相对完整。新增物品已有配置入口；仍需资源 ID、重复 ID、缺失引用及打包加载验收 |
| 背包、快捷栏、箱子容器 | ItemRules 的增删／堆叠／交换，ItemContainer，ItemSlot 拖拽，BagPanel、QuickBar、ChestPanel、ChestWindow | **当前最接近完整闭环的模块**。需实测拆分、满背包、跨箱交换、数量守恒和关闭窗口后的状态 |
| 场景交互与箱子 | IInteractable、InteractBase；玩家范围／可见性检测；F 交互；TestChest 开关动画和窗口事件 | 箱子交互已形成代码路径。可以扩展 NPC、任务机关和存档点，但这些还没实现 |
| 物品选择与手持展示 | 选中槽事件、滚轮快捷栏、HandPos、实例化物品、动画覆盖控制器 | 已有选择到显示的路径。普通物品部分还是二维图标，不能视为完成的三维握持表现 |
| 玩家运动与生命反馈 | CharacterController、移动／跳跃、动画参数、受伤／死亡事件、生命条 | 基础已有。镜头目前以固定偏移跟随为主；完整死亡重试、暂停、输入模式切换还需整合 |
| 武器战斗 | combo 数据、当前武器查询、攻击请求与播放段数分离、动画事件、范围／角度检测、同次检测去重 | **战斗原型**。需要真实扣血、攻击窗口、输入缓存、打断规则、敌人反馈，以及不同武器连击验收 |
| 敌人 | EnemyObj、IDamageable | 当前 TakeDamage 主要打印伤害；没有完整生命、死亡、AI、战利品闭环 |
| 事件与 UI 基础设施 | EventCenter、GameEvents、UIManager、UIBase | 可复用基础设施，不应单独包装成完成的游戏玩法。需检查订阅生命周期与事件所属角色 |
| 场景环境 | 村庄、箱子、地形及环境预制体 | 可作为关卡材料；地图面积不等于关卡完成度，尚需路线、遭遇和引导设计 |
| 对话、任务、Boss、IK、存档 | 本次脚本盘点未发现对应的完整实现 | 按待开发安排，不写成已经完成的成果 |

结论：现阶段可以展示“物品与交互系统原型”，还不能称为完整动作 Demo。接下来应补游戏循环，减少继续扩充同类道具和地图的投入。

## 3. 内容范围与通关流程

### 必须完成的内容

- 一张紧凑关卡：营地、废弃哨站、守卫庭院三个区域，尽量复用现有环境。
- 一名委托 NPC，一条主线任务，约 12～20 个对话节点。
- 两种武器：单手剑与长柄武器；美术／动画资源不足时第二种改为双手重剑，二者只选一个。
- 两种普通敌人：近战哨兵、蓄力重击兵。数量以 4～6 场短遭遇为限。
- 一个两阶段 Boss，基础阶段三种招式，第二阶段增加一种变化。
- 血瓶使用、箱子奖励、快捷栏换武器、任务进度 UI。
- 开始、暂停、操作提示、死亡重试、通关界面、基础设置。
- 一个版本化存档槽：任务阶段、获得的物品、装备、检查点与已领取奖励。

### 建议流程

| 时段 | 玩家行为 | 系统衔接 | 应看到的反馈 |
| --- | --- | --- | --- |
| 0～2 分钟 | 营地与 NPC 对话，接受委托 | 对话启动任务；箱子提供剑和血瓶 | 对话选项、任务追踪、物品提示 |
| 2～5 分钟 | 通过练习区，击败第一名哨兵 | 移动、闪避、攻击、敌人死亡 | 攻击命中、伤害反馈、死亡事件 |
| 5～9 分钟 | 进入哨站，击败重击兵并获得第二武器 | 掉落／奖励进入容器，快捷栏换装 | 武器动作、攻击范围与节奏明显不同 |
| 9～12 分钟 | 取得装置核心并激活庭院入口 | 拾取／交付推进任务，机关读取任务状态 | 路线解锁、检查点激活、Boss 提示 |
| 12～18 分钟 | 挑战守卫 Boss，可就地重试 | 战斗、阶段切换、检查点 | 可读前摇、阶段变化、胜利反馈 |
| 18～20 分钟 | 完成交付、领取奖励、结束展示 | Boss 死亡推进任务，对话发放一次奖励 | 完成状态、奖励到账、通关界面 |

失败后返回 Boss 门前检查点，不要求重走长路或重复对话。目标用时需通过试玩修正，而不是靠增加走路距离凑时长。

## 4. 数据驱动边界

沿用当前项目的思路：**SO 保存设计配置，运行时对象保存会变化的状态。** 不在共享 SO 中保存玩家当前血量、任务完成标记或 Boss 当前阶段。

| 配置资产 | 主要内容 | 对应运行时状态 |
| --- | --- | --- |
| ItemSO | ID、名称、图标、预制体、堆叠、使用／握持配置 | 数量、持有位置、实例状态 |
| WeaponSO | 攻击段列表、动作覆盖、伤害／范围／时序、握持点 | 当前攻击实例、输入缓存、已命中目标 |
| DialogueSO | 节点、文本、选项、条件、结果 | 当前节点、交互对象、一次性执行记录 |
| QuestSO | ID、前置、目标列表、奖励 | 未接取／进行中／可交付／已完成、目标计数 |
| EnemySO／BossSO | 生命、移动、招式、感知与阶段阈值 | 当前生命、目标、状态、冷却、阶段 |

事件携带必要的主体：谁攻击、谁死亡、哪一个任务／敌人实例。当前全局只传一个连击 index 的广播，在多角色或多把活动武器情况下容易误触发；正式战斗阶段要带持有者身份，或直接调用当前装备武器。

ID 用于查找和存档；运行过程中用明确的对象引用，不把所有逻辑都变成字符串判断。任务、对话和战斗分别负责自己的状态修改，UI 读取结果并展示。

## 5. SO 驱动对话

第一版采用 Inspector 可编辑的节点列表，不先制作大型节点图编辑器。

每个节点包含稳定节点 ID、说话人、正文、选项及后继节点。选项可附带条件与结果，但限制在本 Demo 真正需要的类型：

- 条件：任务是否开始／完成，是否持有指定物品，Boss 是否已击败。
- 结果：接受任务、交付任务、发放一次性奖励、结束对话。
- 显示：可跳过打字效果，确认推进，选项按钮，退出交互。

示例：未接取时显示“接受委托”；进行中提示核心位置；核心已获得时允许开启庭院；Boss 击败后开放交付；已完成时只显示后续台词。

对话开启时锁定攻击、移动和快捷栏输入；退出后恢复。采用统一输入模式（Gameplay／Dialogue／Menu），避免只在某个 UI 中拦一次鼠标。

验收：创建第二份 DialogueSO 不改播放器代码；节点不存在能在编辑阶段发现；重复对话不能重复发奖励；退出和重新进入不会让输入永久锁死。

## 6. 任务系统

只做一条主线，但基础目标支持对话、击败目标、收集／交付物品、交互机关四种。

主线步骤：接受委托 → 击败哨站守卫 → 获取核心 → 激活庭院 → 击败 Boss → 返回交付。

规则必须明确：

- 击杀进度由“敌人死亡”触发，不由每次伤害触发；同一敌人实例只计数一次。
- “持有 N 个物品”实时查询背包／快捷栏；“累计获取”是另一种目标，不混用。
- 已经持有的任务物品，在接任务时也要检查，不要求丢掉再捡。
- 交付物品、标记完成、发奖励作为一次完整操作处理。背包空间不足时保留可交付状态并说明原因。
- 奖励只发一次；读取存档后不能再次领取。

验收：重复事件不重复完成；退出重进保留进度；领取奖励后再次交谈无重复发放；玩家没有先跟 NPC 对话也不会卡死核心流程。

## 7. 多武器战斗

### 两种武器必须改变操作选择

以下数值仅是初始调参方案：

| 武器 | 连击 | 节奏与范围 | 代价 | 用途 |
| --- | --- | --- | --- | --- |
| 单手剑 | 3 段 | 前摇短、距离近、转向灵活 | 单次伤害与削韧较低 | 近身试探、闪避后反击 |
| 长柄武器 | 2 段 | 距离更长、前方攻击突出 | 前摇／后摇更长，转向受限 | 保持距离、抓 Boss 大硬直 |

不要仅替换模型和伤害数字。两把武器至少在攻击时序、有效范围、位移与取消窗口中体现差异。

### 攻击模型

一次攻击有准备、有效命中、收招三个阶段。输入只提出请求，实际动画状态决定当前段；命中事件决定何时进行检测。

- 当前工程已分离“待执行请求”和“播放段数”，但还没有完整输入缓存窗口。
- 增加约 0.15～0.25 秒的单次输入缓存作为初始值；只缓存一个下一段请求，过期丢弃。
- 武器配置连击长度；当前 Animator 只有三段，首版使用两段和三段武器，不承诺仅加 SO 就支持任意段数。
- 每次挥击有 attackInstanceId，多个采样帧共享命中集合；一次挥击对同一敌人默认一次伤害。多段伤害显式配置 hitId，不把重复检测当成多段攻击。
- 换武器、受击、死亡要取消攻击与缓存；明确旧动画过渡中的事件不能打到新武器上。
- WeaponData 是当前物品运行数据，WeaponObj 不再各自制造不同步的伤害状态。

先用现有范围／角度检测做稳定的命中，再考虑扫掠检测。提供 Gizmos 显示判定中心、方向、半径、当前攻击实例，便于解释误命中和漏命中。

验收：快速点击不会跳伤害段；两段武器不会触发第三段；一个敌人多个 Collider 不重复扣血；攻击中换装不继承上一把武器的伤害；背包／对话期间不能攻击。

## 8. 普通敌人与 Boss

普通敌人先完成最小状态集合：待机、发现、追击、攻击、受击、死亡、脱战返回。两种敌人共用基础移动和伤害逻辑，差异通过动作与攻击参数体现。

Boss“失控守卫”使用可解释的状态机，不在第一版引入通用行为树编辑器。

| 招式 | 预警 | 玩家应对 | 惩罚窗口 |
| --- | --- | --- | --- |
| 横扫 | 抬武器并转肩 | 后退或闪避通过 | 挥空后的短收招 |
| 重砸 | 明显举起武器 | 侧移离开落点 | 长收招，适合重武器 |
| 冲刺 | 压低身体、锁定方向 | 横向闪避 | 停止后的转身硬直 |
| 二阶段追加震荡 | 保留重砸前摇，增加可见二次预警 | 不贪第一下收招 | 第二次攻击结束后 |

初始建议在 50% 生命进入第二阶段，切换只触发一次。通过追击能力和招式组合变化提高压力，不单纯提高攻击速度。Boss 不应在没有任何提示的情况下瞬间改变攻击方向。

验收：所有招式有前摇和可反击窗口；死亡只结算一次；玩家死亡后 Boss、血瓶补给和场地按检查点规则重置；Boss 不因玩家绕柱或离开范围永久卡死。

## 9. IK 与握持表现

先解决三维物品、骨骼挂点和姿势动画，再加入 IK。当前二维血瓶图标不能用于最终近景握持展示，必须补一个简单三维瓶子。

顺序：

1. 每种武器／物品校准握持中心、局部旋转和缩放。
2. 手指动画层只控制明确的手指骨骼；握剑、握瓶使用不同姿势。
3. 长柄武器提供副手 GripTarget，使用左臂双骨 IK 跟随目标，配置肘部提示点。
4. 攻击、换装和使用物品时控制 IK 权重，避免手被目标强行锁住。
5. 坡地脚部 IK 作为后续增强项，只有主流程稳定后再做。

工程目前的 Warrior 是 Generic 骨架；IK 实施前确认所选方案支持该骨架。可以评估 Animation Rigging 的双骨约束，不直接把 Humanoid 的 Animator IK 用法套上去。本案不要求先把整套模型改成 Humanoid。

验收：静止、跑步、攻击、换装时副手不会突然飞走；肘关节不明显反折；权重切换平滑；IK 不改变实际战斗判定。

## 10. 手感优化清单

先保证攻击响应、命中时机与规则准确，再增加视觉效果。

| 优先级 | 项目 | 验收方式 |
| --- | --- | --- |
| P0 | 输入响应与缓存 | 快速点击、提前点击、窗口外点击结果一致且可解释 |
| P0 | 命中同步 | 慢放时判定出现于有效挥击段，不在抬手前扣血 |
| P0 | 闪避与打断 | 无敌窗口、受击打断、换装规则明确；UI 不吞掉释放后的输入状态 |
| P1 | 打击反馈 | 命中音效、粒子、敌人受击动作；不同武器有可辨节奏 |
| P1 | 短暂停顿 | 命中停顿按攻击力度调节；UI／输入计时不因暂停逻辑失效 |
| P1 | 镜头 | 可控跟随、遮挡处理、适量震动；提供震动开关／强度 |
| P1 | 朝向与位移 | 攻击前可调整方向，出招后转向受限，移动不与 Root Motion 双重叠加 |
| P2 | 轻度目标辅助 | 只辅助合理范围内目标，避免穿墙吸附和突然大幅旋转 |

帧率目标暂定目标 Windows 测试机 1080p 下稳定接近 60 FPS；记录硬件、画质、场景和 Profiler 数据后再给出对外性能结论，不预先宣称优化成果。

## 11. 存档、重试与发布

只做一个存档槽和少量检查点，不做任意时刻完整世界快照。

保存：版本号、任务阶段、物品 ID 与数量、当前装备 ID、一次性奖励记录、检查点、已完成遭遇。加载时通过配置表重建运行数据，不直接序列化 Animator、GameObject 或 SO 引用。

Boss 死亡前退出，重进按检查点重置 Boss；胜利后退出保留完成状态。玩家死亡只重置当前遭遇，不回退已领取的前置任务奖励。血瓶数量和补给重置规则在检查点中统一定义。

交付包含开始游戏、继续、设置、退出；暂停菜单；死亡重试；通关页。第一次无存档启动也必须能完成全流程。构建包实测 Addressables、场景列表、资源路径、鼠标状态和编辑器代码隔离。

## 12. 开发路线与每阶段交付

以下是单人开发的工作量预算，不是承诺工期；按每周约 20 小时、可复用现有模型动画估算。若需要从零制作动作，单独增加预算。

| 阶段 | 建议工作量 | 可验收产物 |
| --- | --- | --- |
| M0：冻结基线 | 6～10 小时 | 建立版本控制与备份；整理来源；修复编译／资源引用；导出能启动的 Windows 包 |
| M1：单敌人战斗闭环 | 20～30 小时 | 一把剑、一名敌人、真实扣血／死亡、动画事件、单次命中、玩家重试 |
| M2：任务串起关卡 | 20～30 小时 | NPC 对话、接取／推进／交付、箱子奖励、短路线；可走到暂用终点 |
| M3：第二武器与手感 | 20～30 小时 | 两／三段连击差异、输入缓存、闪避、血瓶、握持姿势、副手 IK |
| M4：Boss | 25～40 小时 | 两阶段 Boss、三种基础招式、检查点重试、胜利推进任务 |
| M5：完整交付 | 20～30 小时 | 存档、菜单、设置、构建验收、性能记录、演示视频与技术说明 |

总预算约 111～170 小时，约 6～9 周；美术补齐与反复调动画可能延长。每阶段结束都留一个可运行构建，避免所有功能做到一半才开始整合。

如果时间缩短：保留一条主线、两种武器和一个 Boss；把第二种小怪改成参数变体，去掉脚部 IK、复杂分支对话和可选任务。不要砍死亡重试、输入可靠性和打包验证。

## 13. 回归验收

- 容器：增删／拆分／交换后数量守恒，满背包不吞物品，关闭箱子后无残留输入。
- 选择：武器→物品→空格→武器连续切换，模型、动画、运行数据一致。
- 连击：快速点击、两段武器、攻击末尾点击、受击、换装、死亡均不错段。
- 生命周期：反复装备／销毁武器后，每次动画事件只到当前持有者的当前武器。
- 命中：同一攻击多 Collider 只扣一次，多段攻击按显式规则分别扣血。
- 任务：重复死亡事件、重复交谈、读档、背包满时交付均无重复奖励。
- Boss：进入战斗、阶段切换、死亡、重试连续多轮，不留旧状态和计时器。
- 资源：打包后首次启动能加载所有配置；无编辑器 API 被带入运行时代码。
- 全流程：从新游戏到通关，在独立构建中连续完成至少三次，记录阻断问题并回归。

纯数据规则优先做 EditMode 测试；动画事件、生命周期、命中和 UI 输入做 PlayMode／场景验收。编译通过只证明语法与引用，不代表上述流程通过。
